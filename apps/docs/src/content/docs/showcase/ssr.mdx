**"SSR support" is easy to claim and easy to fake.** Plenty of component
libraries render a placeholder on the server and call it SSR. The test that
matters is simpler: *does the browser paint the finished UI before a single
byte of JavaScript runs?* With Declarative Shadow DOM (DSD) the answer is yes
— the server serializes each component's shadow root, styles included, into
`<template shadowrootmode="open">`, and the browser's HTML parser attaches it
during parsing. No JS, no flash of unstyled content, no layout shift.

The demo below puts the two strategies side by side. The left pane **is**
server-rendered — the markup you see was generated by
`@awc-ui/core/hydrate`'s `renderToString()` and shipped inside this very
page's HTML, so it paints the moment the document parses. The right pane
replays what the same card looks like when components exist only as inert
tags until a JavaScript bundle arrives.

## The left pane is not a simulation

Open `view-source:` on this page (or press <kbd>Ctrl</kbd>+<kbd>U</kbd> /
<kbd>Cmd</kbd>+<kbd>Option</kbd>+<kbd>U</kbd>) and search for
`shadowrootmode="open"`. You will find the left pane's `md-button`,
`md-switch`, and `md-status-dot` with their complete shadow DOM — structure
*and* styles — inlined as `<template shadowrootmode="open">` blocks in the
server response. That markup was produced by `renderToString()` from
`@awc-ui/core/hydrate` and pasted into this page at build time, which makes
this page its own proof: the HTML parser attaches those shadow roots and
paints the finished card before the docs site's JavaScript is even requested.

Two things about the left pane stay true after load:

- **It hydrated.** When this page's element loader eventually runs, the
  client runtime finds the server-rendered DOM (the `s-id` annotations you
  can also see in view-source) and *adopts* it instead of re-rendering —
  toggle the switch, it's live. Nothing was thrown away or repainted.
- **What is simulated is only the clock.** The Replay button compresses a
  slow connection into a 1.9-second story so you can watch the order of
  events. The order itself — DSD paints at HTML-parse time, client-only
  rendering paints at JS-execution time — is how the two strategies behave
  everywhere.

## How `@awc-ui/core/hydrate` renders on the server

Every AWC UI build ships a second compilation of the whole library, the
*hydrate app*, made to run in Node rather than a browser. `renderToString()`
spins up a lightweight server-side DOM, instantiates each custom element it
finds in your HTML, runs its actual `render()`, and serializes the result:

```js
import { renderToString } from "@awc-ui/core/hydrate";

const { html } = await renderToString(
  `<md-button variant="filled">Add to cart</md-button>`,
  {
    fullDocument: false, // return a fragment, not a whole <html> document
    serializeShadowRoot: "declarative-shadow-dom", // the default
  },
);
// html now contains <md-button ...><template shadowrootmode="open">…
```

The details that make it production-usable:

- **Real shadow DOM, declaratively.** With
  `serializeShadowRoot: "declarative-shadow-dom"` (the default), each
  component's shadow root — including its stylesheet — is emitted as a
  `<template shadowrootmode="open">` child, so browsers reconstruct genuine
  shadow roots during HTML parsing. You can mix strategies per component:
  `{ "scoped": ["md-tooltip"], default: "declarative-shadow-dom" }`.
- **Hydration, not re-rendering.** `clientHydrateAnnotations` (on by
  default) embeds the comments and `s-id` attributes the client runtime uses
  to reconnect to the existing DOM. First paint survives; event listeners
  attach to the nodes already on screen.
- **Streaming.** Pass `true` as the third argument and `renderToString()`
  returns a Node `Readable` instead of a promise — drop it straight into a
  streaming SSR pipeline.
- **Escape hatches.** `excludeComponents` leaves chosen tags untouched,
  `constrainTimeouts` keeps a component's timers from stalling the server
  render, and `prettyHtml` formats output for debugging.

Frameworks never call this by hand in practice — their integrations do it
per request or at build time, which is exactly what the reference apps below
demonstrate.
