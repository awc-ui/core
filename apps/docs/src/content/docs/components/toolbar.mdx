**A container for controls that stay visible.** Icon buttons, buttons, text
fields — optionally paired with a FAB — in two variants: `docked`
(bottom-anchored, replacing the legacy bottom app bar) and `floating`
(free-placed, pill-shaped). It implements the WAI-ARIA **toolbar** pattern, so
the whole cluster of buttons is a single Tab stop.

## Install

:::caution[The toolbar has no actions of its own]
The host is a container. Hover, press and `Space` / `Enter` all come from the
slotted controls, each following its own component's rules. What the toolbar
adds is the **grouping**: one role, one accessible name, one Tab stop.
:::

## When to use

- A set of controls that should stay **visible and available**, not hidden
  behind a trigger.
- The primary actions for a screen, anchored at the bottom (`docked`).
- A contextual cluster near what it acts on — a formatting bar, a drawing
  palette (`floating`).

### When not to use

| Situation | Use instead |
|---|---|
| Actions that can hide behind a trigger | [`md-menu`](/components/menu/) |
| The screen's header and title | [`md-app-bar`](/components/app-bar/) |
| Top-level destinations | [`md-navigation-bar`](/components/navigation-bar/) / [`md-navigation-rail`](/components/navigation-rail/) |
| 3+ related actions acting as one unit | [`md-button-group`](/components/button-group/) |
| One primary action alone | [`md-fab`](/components/fab/) |
| Sibling views inside a screen | [`md-tabs`](/components/tabs/) |

### Decision cues

| Need | Setting |
|---|---|
| Bottom bar for a screen's main actions | `variant="docked"` (default) |
| A contextual pill near the content | `variant="floating"` |
| A column of controls | `variant="floating"` + `layout="vertical"` |
| A tinted, high-emphasis bar | `color="vibrant"` |
| Where controls sit along the bar | `alignment="start"` / `"center"` / `"end"` / `"space-between"` |
| A paired primary action | The `fab` slot |
| No toolbar semantics at all | `container-semantics="generic"` |

## Variants

| Variant | Shape | Use for |
|---|---|---|
| `docked` | Full-width, `position: sticky` | **Default.** A screen's primary actions |
| `floating` | Inline, pill-shaped, hugs its content | Contextual and formatting bars |

:::caution[`docked` is `position: sticky`, not `fixed`]
Sticky positions against the nearest **scroll container**, so the toolbar must
sit inside that container — typically as its last child — for bottom-bar
behaviour. If you want the bar pinned to the viewport regardless of document
structure, wrap it in your own `position: fixed` element.
:::

:::note[The scheme only reaches **direct** slotted icon buttons]
The toolbar retints `md-icon-button` children so a row of them reads as one
unit. Two limits worth knowing:

- The same `md-icon-button` **outside** a toolbar keeps its normal colours —
  this library never changes icon-button defaults globally.
- An icon button nested inside a wrapper element still joins the roving group,
  but keeps its own palette. Slot them directly if you want the tint.

Only `standard` and `outlined` ink is tinted. `filled` and tonal-toggle buttons
keep their own container fill, so a selected toggle never flattens into looking
unselected.
:::

## Pairing a FAB

The `fab` slot places a FAB beside the bar — or below it under
`layout="vertical"`. On a **floating** toolbar the FAB is a separate control
with its own elevation, sitting next to the pill. On a **docked** toolbar it is
flattened so it reads as part of the same bottom bar.

:::note[The FAB is its own Tab stop]
It is deliberately **not** part of the roving group — a distinct role deserves a
distinct stop. Tab reaches the button cluster, Tab again reaches the FAB.
:::

## Overflow

The toolbar **does not clip or scroll by default** — focus rings stay visible,
which is the point. M3's guidance is to cap the action count or move the excess
into an overflow [`md-menu`](/components/menu/). When you must, opt in:

| Custom property | Effect |
|---|---|
| `--md-toolbar-overflow-x: auto` | Scroll horizontally |
| `--md-toolbar-overflow-y: auto` | Scroll a vertical floating toolbar |
| `--md-toolbar-flex-wrap: wrap` | Wrap onto more rows instead of scrolling |

## Events

`md-toolbar` emits **no events**. It is a container: listen to the controls you
slotted into it. `setFocus()` is the one method, for moving focus into the
toolbar's current roving stop programmatically.

## Accessibility

The toolbar implements the
[WAI-ARIA toolbar pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/):
`role="toolbar"` on the host, one accessible name, and a roving tabindex that
turns the whole button cluster into a **single** Tab stop.

- **Name it.** There is no default `aria-label` — set one (`"Text formatting"`),
  or `aria-labelledby` when a visible label exists. An unnamed toolbar logs a
  dev-mode warning.
- `aria-orientation` follows `layout`.
- A **soft-disabled** (`aria-disabled`) control stays in the roving group and
  arrow-reachable, per APG — disabled toolbar items stay discoverable. The
  initial Tab stop prefers an enabled control.
- An author `tabindex="-1"` on a native control opts it out of the group.
- The paired FAB keeps its own Tab stop.

### Keyboard

| Key | Action |
|---|---|
| `Tab` | Into the button cluster's current stop; `Tab` again moves **out** — the cluster is one stop |
| `←` / `→` | Move within a horizontal group, wrapping (follows reading direction under RTL) |
| `↑` / `↓` | Move within a vertical floating group |
| `Home` / `End` | First / last control |
| `Space` / `Enter` | Activate the focused control, per its own pattern |

Off-axis arrows are ignored, and modifier chords (`Shift`/`Ctrl`/`Meta`/`Alt` +
arrow) pass straight through.

### What stays out of the roving group

This is the part that surprises people. Only **activator** controls rove —
`md-icon-button`, `md-button`, native `<button>` / `<a href>`, and
`role="button"` / `menuitem` / `link`. Everything else keeps its own Tab stop
and its own native behaviour:

| Kind | Examples |
|---|---|
| Text and value entry | `<input>`, `<textarea>`, `contenteditable`, `md-text-field`, `md-select`, `<select>`, `type="range"` |
| Self-managing composites | `md-button-group`, `md-menu`, `role="radiogroup"` |
| **All** toggles | `md-switch`, `md-checkbox`, `md-chip`, `<input type="checkbox">` / `radio`, `role="checkbox"` / `radio` |

That is what keeps caret movement, text selection, value adjustment and each
composite's own arrow handling working — and it means native and `md-*` toggles
behave identically when mixed in one bar.

### The generic container

`container-semantics="generic"` drops `role="toolbar"`, every toolbar `aria-*`,
and **all roving / arrow navigation**. Slotted controls keep their own roles,
labels and natural tab order — for a mobile or non-semantic shell.

:::caution[A generic container cannot be named]
ARIA prohibits naming `role="generic"` elements, so assistive tech ignores
`aria-label` / `aria-labelledby` here. The component leaves the attribute in
place — it is yours, and it survives a runtime switch back to
`container-semantics="toolbar"` — but logs a dev-mode warning so the ignored
name is not a silent surprise. If the group deserves a name, it deserves
`container-semantics="toolbar"`.
:::

**i18n** — everything user-facing is either an `aria-label` you set on the

re-check [overflow](#overflow) per locale.
