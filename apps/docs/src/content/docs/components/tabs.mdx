**Switch between sibling views within one screen.** `md-tabs` is the strip
only: it owns the active index, the roving focus and the indicator. The content
lives in a separate [`md-tab-panels`](/components/tabs/#md-tab-panels) region, and each
tab is a [`md-tab`](/components/tabs/#md-tab) child.

## When to use

- **Peer categories of related content** on one screen: Overview / Activity /
  Settings.
- The user should be able to move between them freely, in any order.

### When not to use

| Situation | Use instead |
|---|---|
| Sequential content meant to be read in order | Hierarchy in the content — typography and spacing |
| A linear process with validation | [`md-stepper`](/components/stepper/) |
| Top-level app destinations | [`md-navigation-bar`](/components/navigation-bar/) / [`md-navigation-rail`](/components/navigation-rail/) |
| Independent collapsible sections | [`md-accordion`](/components/accordion/) |
| Choosing a value or mode | [`md-segmented-button`](/components/segmented-button/) |
| Actions rather than views | [`md-button-group`](/components/button-group/) / [`md-toolbar`](/components/toolbar/) |
| Many categories that won't fit | [`md-select`](/components/select/), or a menu |

:::caution[`md-tabs` has no `density` prop]
One of the few components without one. Density lives on the individual
[`md-tab`](/components/tabs/#md-tab) children.
:::

### Decision cues

| Need | Setting |
|---|---|
| Top-level sections of a screen | `variant="primary"` (default) |
| Sub-sections inside a primary tab's panel | `variant="secondary"` |
| Equal-width tabs filling the strip | `tab-width="equal"` (default) |
| Tabs sized to their labels | `tab-width="auto"` |
| More tabs than fit | They scroll — no prop needed |
| Wire tabs to panels for you | Wrap panels in `md-tab-panels` |
| Tighter rows | `density` on each `md-tab` |

## Variants

`primary` is for the top-level tab set on a surface; `secondary` is for a nested
set inside a primary one. The **children carry their own `variant`** — the strip
propagates its value to them, so keep them consistent if you also set it by
hand.

## Tab width and strip width

Two separate knobs, and confusing them is the usual bug.

| Prop | Controls | Values |
|---|---|---|
| `tab-width` | How each **tab** sizes along the strip | `equal` (default, share the parent's full width) · `auto` (content width, strip scrolls) · any CSS length, e.g. `140px` |
| `width` | The width of the **whole strip** | Any CSS size. Default: `100%` of the parent |

:::caution[A shrink-to-fit parent lets the panel resize the strip]
In an inline-block card, an auto grid column or a flex item, the parent's width
follows the **active panel**. Switch to a tab whose content is one letter and
the whole tablist collapses. Either set `width` to anchor the strip, or — better
— use [`md-tab-panels`](/components/tabs/#md-tab-panels), whose default
`sizing="stable"` keeps the region the size of the largest panel.
:::

## Pairing with panels

`md-tabs` renders no content. Put a
[`md-tab-panels`](/components/tabs/#md-tab-panels) region directly after the strip with
one [`md-tab-panel`](/components/tabs/#md-tab-panel) per tab, in tab order. The region
finds the nearest preceding `md-tabs` sibling (or point `for` at its `id`),
follows `mdTabChange` itself, and wires the ARIA both ways — `aria-controls` on
each tab, `aria-labelledby` on each panel, ids auto-assigned where missing.

If you are wiring your own panels instead, they must be in the **same DOM
scope** as the tabs — `controls` is an IDREF, and IDREFs don't cross shadow
boundaries.

## Events

| Event | Cancelable | Detail | Fires |
|---|---|---|---|
| `mdTabChange` | no | `{ index, previousIndex }` | The active tab changed — click, keyboard, or `selectTab()` |

Re-activating the already-active tab does **not** emit. Out-of-range
`selectTab()` calls are ignored, and setting `activeTabIndex` as a property
normalizes (rounds and clamps) **without** emitting — the property path is
consumer-initiated, so you already know.

## The sub-components

A tabbed view is composed from three sub-components. They are documented here
rather than on their own pages: none of them mean anything outside a tabbed
view, and the strip owns the active index for all of them.

### `md-tab`

**One tab in the strip** — a label and/or icon, an optional badge, and the
active indicator.

:::caution[Four things that bite]
- **`active` is managed by `md-tabs`** through its `active-tab-index` (or
  `selectTab()`). Setting `active` by hand on several tabs gives you two sources
  of truth and desynchronises the indicator.
- **`variant` exists on both the strip and each tab, and must match.** The tab
  does **not** inherit it from the parent — the default is `primary` on both.
- **`controls` takes the panel's `id`, and IDREFs cannot cross a shadow
  boundary.** Tab and panel must live in the same DOM scope.
- **`mdTabClick` is internal** — no payload, low-level. Application code listens
  to the strip's `mdTabChange`, whose detail is `{ index, previousIndex }`.
:::

- `inline-icon` switches icon+label from stacked to side-by-side.
- `badge=""` (empty string) renders a dot badge rather than no badge.
- **Unlike `md-tabs`, `md-tab` does have a `density` prop** — set density here,
  not on the strip.

<ApiTable {...tabApi} />

### `md-tab-panels`

**The content half of a tabbed view** — holds one
[`md-tab-panel`](#md-tab-panel) per tab, follows the strip's active index, and
controls how the region is sized as panels change.

- **It wires itself.** The region listens for the strip's `mdTabChange` and sets
  `active` / `inert` on the panels. You do **not** toggle `active` by hand — and
  you do not need a `mdTabChange` listener just to switch panels.
- **ARIA is wired both ways**: each tab gets `aria-controls`, each panel gets
  `aria-labelledby`, and ids are auto-assigned where missing. Set your own
  `id` / `controls` only when you need stable, meaningful ids.
- `for` resolves against the panel region's own root, so the strip must be in the
  **same DOM scope** — IDREFs don't cross shadow boundaries.
- Panels are matched to tabs **by position**, so keep them in tab order.
- Neither this nor [`md-tab-panel`](#md-tab-panel) has a `density` prop.
- Panels are **not lazily rendered**: inactive panel content stays in the DOM.
  Mount expensive content yourself on first activation.

<ApiTable {...tabPanelsApi} />

### `md-tab-panel`

**The content of one tab.** A single `active` flag decides whether it is shown;
everything else is your content. The host renders `role="tabpanel"` and takes a
`tabindex` of `0` while active, `-1` otherwise.

- **`active` is the entire API — and the parent owns it.**
  [`md-tab-panels`](#md-tab-panels) sets `active` and `inert` from the strip's
  `mdTabChange`. Setting `active` yourself fights it, and two active panels is an
  ambiguous state.
- **The id ↔ tab association is automatic.** The region assigns ids where they
  are missing and sets `aria-controls` / `aria-labelledby` both ways. Give the
  panel a stable `id` only when you want a meaningful one (deep links, tests) —
  and then match it with the tab's `controls` in the **same DOM scope**, because
  IDREFs don't cross shadow boundaries.
- **Inactive panels keep their layout box** — that is what makes the region
  size-stable — but their content is `visibility: hidden` and the host is
  `inert`, so it is out of paint, hit-testing and the accessibility tree.
- Content of inactive panels **stays in the DOM**. Mount expensive widgets on
  first activation.
- No `density` prop.

## Accessibility

- Give the strip an `aria-label` naming what the tabs switch between.
- The strip manages roving focus: one tab stop for the whole set, arrow keys to
  move (they wrap), `Home` / `End` to jump to the ends. Arrow direction follows
  the **visual** order, so it inverts under RTL.
- Disabled tabs are skipped by the arrow-key tour.
- Wire each tab to its panel: [`md-tab-panels`](/components/tabs/#md-tab-panels) does it
  for you, otherwise set the tab's `controls` to the panel's `id`. Both must be
  in the same DOM scope — IDREFs don't cross shadow boundaries.
- Keep exactly one tab active; an empty tab set has no valid state.

### Keyboard

| Key | Action |
|---|---|
| `Tab` | One stop for the whole strip (roving tabindex), then into the active panel |
| `←` / `→` | Move between enabled tabs, wrapping at the ends (inverted under `dir="rtl"`) |
| `Home` / `End` | First / last enabled tab |
| `Enter` / `Space` | Activate the focused tab |

## Theming

| Custom property | Purpose | Default |
|---|---|---|
| `--md-tabs-container-color` | Strip background | `surface` |
| `--md-tabs-divider-color` | Rule under the strip — read by each child tab's own divider default | `outline-variant` |

properties documented on [`md-tab`](/components/tabs/#md-tab).

## CSS parts

| Part | On | Element |
|---|---|---|
| `container` | `md-tabs` | The scrollable tab container |
| `content` | `md-tab` | Icon + label wrapper |
| `icon` | `md-tab` | The glyph |
| `label` | `md-tab` | Label text |
| `indicator` | `md-tab` | The active bar |
| `divider` | `md-tab` | This tab's slice of the rule under the strip |
| `state-layer` | `md-tab` | Hover / focus / press overlay |

`md-tab-panels` and `md-tab-panel` expose **no** parts — they are layout and
plumbing, with nothing of their own to paint.
