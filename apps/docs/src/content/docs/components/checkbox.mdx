## When to use

- Several **related** options where any number may be selected.
- A single opt-in that must be **submitted with a form** (terms, consent) —
  note this needs an explicit submit to take effect, unlike a switch.
- A **parent/child** selection tree, using `indeterminate` for the partial
  state.

### When not to use

| Situation | Use instead |
|---|---|
| Exactly one option from a list | [`md-radio`](/components/radio/) |
| A setting that takes effect **immediately** | [`md-switch`](/components/switch/) |
| More than ~7 options, or space is tight | [`md-multi-select`](/components/multi-select/) |
| Assigning a subset from a large pool | [`md-transfer-list`](/components/transfer-list/) |
| Filtering by removable criteria | [`md-chip`](/components/chip/) |
| Two opposing choices (on/off framing) | [`md-switch`](/components/switch/), or [`md-button-group`](/components/button-group/) |
| Running an action | [`md-button`](/components/button/) |

### Decision cues

| Need | Setting |
|---|---|
| Independent on/off choices | This component |
| A mixed "some children checked" state | `indeterminate` |
| A hint under the control | `supporting-text` |
| A validation message | `error-text` |
| Blocks form submission when unchecked | `required` |
| Unavailable but still discoverable | `soft-disabled` |
| Smaller box | `density="-1…-4"` |

## Labelling — there is no slot

:::danger[`<md-checkbox>Label</md-checkbox>` renders nothing]
The component has **no default slot**. Text placed between the tags is
discarded, and a bare checkbox has no accessible name at all (axe
`aria-toggle-field-name`). Wrap it in a `<label>` — that gives both the name
and a larger hit target — or set `aria-label` / `aria-labelledby` on the host.
:::

## States

Five states, three of them value-carrying and two of them availability
modifiers:

| State | Set with | Notes |
|---|---|---|
| Unchecked | *(default)* | `checked` absent |
| Checked | `checked` | Submits `value` under `name` |
| Indeterminate | `indeterminate` | `aria-checked="mixed"` — presentation only |
| Disabled | `disabled` | Skipped by `Tab` |
| Soft-disabled | `soft-disabled` | Same visuals, still focusable |

## Indeterminate is a presentation state

`indeterminate` renders the dash and exposes `aria-checked="mixed"`. It is
**not** a third user-selectable value: a click resolves the checkbox to
checked or unchecked and clears the flag. A parent checkbox therefore has to
recompute it every time a child changes.

## Supporting and error text

A checkbox has nowhere else to show a failed `required` except the browser's
transient validation balloon, so it carries its own message line. One line is
rendered, and `error-text` wins it whenever it is set — the component renders
`errorText || supportingText`. `error` does not choose between them: it
recolours that line to the error role and gives it `role="alert"`.

:::caution[`error` colours the line, `aria-invalid` colours the box]
Three separate signals, easy to conflate:

| Want | Set |
|---|---|
| The message line in the error colour, announced live | `error` |
| A different message while invalid | `error-text` (shown whenever set) |
| The **box** outlined/filled in the error colour | nothing — the host sets `aria-invalid` itself |

The box recolour is driven by `:host([aria-invalid="true"])`, and the component
sets `aria-invalid` when `required` is unsatisfied or `setCustomValidity()`
holds a message. Setting `error` alone leaves the box in its normal colours;
setting `required` on an unchecked box recolours it whether or not you set
`error`.
:::

:::caution[Don't show both at once]
Swap supporting → error rather than stacking them. Two lines where there was
one shifts the layout under the user's pointer.
:::

:::note[Wrap the label text when a message is present]
A checkbox carrying a message stacks as **[touch target, message]**, so a bare
text node beside it aligns to the *top of the touch target* rather than to the
box — about 15px high. Put the label in a `<span>` given the target's height and
centred, as the snippets below do.
:::

## Forms

`md-checkbox` is form-associated through `ElementInternals`. When checked it
submits `value` (default `"on"`) under `name`, and it restores its authored
state on form reset. **Don't add a hidden `<input>`** — the mirror
double-submits.

`required` genuinely blocks submission. `value-missing-label` is a prop rather
than a hardcoded string precisely so you can localize the "please check this
box" message.

**Methods** — `getValidity()`, `checkValidity()`, `reportValidity()` and
`setCustomValidity(message)` mirror the native constraint-validation API. Use
`setCustomValidity('')` to clear a server-side message.

## Events

| Event | Cancelable | Detail | Fires |
|---|---|---|---|
| `mdChange` | no | `{ checked, indeterminate }` | Whenever the state changes |
| `mdValidityChange` | no | `{ valid, validationMessage, flags }` | Only when validity **changes** |

Both details are inline shapes — there is no exported `…Detail` type for either.
The typed handle the library does export is `MdCheckboxCustomEvent<T>`:

```ts
import type { MdCheckboxCustomEvent } from '@awc-ui/core';

type ChangeEvent = MdCheckboxCustomEvent<{
  checked: boolean;
  indeterminate: boolean;   // always false after a user click
}>;

type ValidityEvent = MdCheckboxCustomEvent<{
  valid: boolean;
  validationMessage: string;
  flags: Record<string, boolean>;   // e.g. { valueMissing: true }
}>;
```

:::caution[`mdValidityChange` is not composed]
It deliberately does **not** cross shadow boundaries, so a delegated listener
on an ancestor in another shadow root will never see it. Bind it on the
checkbox itself. `mdChange` *is* composed, so one delegated listener on a
light-DOM wrapper catches every checkbox inside it.
:::

:::tip[The first validity state is not a change]
`mdValidityChange` primes its baseline on mount and stays silent, so a page of
required checkboxes does not emit one event per control on load. Read the
starting state with `getValidity()` instead.
:::

## Accessibility

- Wrapping in `<label>` gives both the accessible name and a larger hit target
  — the preferred pattern. Otherwise use `aria-label` or `aria-labelledby`.
- Tri-state is exposed as `aria-checked="mixed"` when `indeterminate`.
- `disabled` leaves the tab order; `soft-disabled` stays focusable.
- Errors surface in `error-text` next to the control, not only in a transient
  browser balloon.
- The hit area is a full 48px at density 0, comfortably over the WCAG 2.5.8
  target size. It tapers 4px per density rung (down to a 32px floor), so a dense
  layout that still has to be tappable needs
  `--md-checkbox-touch-target-size` raised by 4px per rung — `64px` at `-4` to
  get 48px back.
- Group related checkboxes in a `fieldset` with a `legend`, or a container with
  `role="group"` and an `aria-label`.

flush with its parent instead of stepping in from it.

### Every density rung

`density="-1…-4"` shrinks the box (18px → 14px, 1px per rung) and the touch
target (48px → 32px, 4px per rung). The state layer is `min(40px, target)`, so
it holds at 40px through rung -2 and only starts shrinking at -3. See
[Density](/behaviour/density/).

| Rung | Box | Touch target | State layer |
|---|---|---|---|
| `0` | 18px | 48px | 40px |
| `-1` | 17px | 44px | 40px |
| `-2` | 16px | 40px | 40px |
| `-3` | 15px | 36px | 36px |
| `-4` | 14px | 32px | 32px |

:::caution[The hit area shrinks too — and the custom property will not pin it]
Each rung trims 4px off the touch target as well as the box, floored at 32px,
so a `-4` checkbox is a 32px target: fine for a dense data table on a mouse,
genuinely hard to hit on touch.

`--md-checkbox-touch-target-size` is the **input** to that subtraction, not the
result:

```css
/* the component's own calc */
--_touch-size: max(32px, calc(var(--md-checkbox-touch-target-size, 48px)
                              + var(--md-sys-density-scale, 0) * 4px));
```

So setting it "back to 48px" at rung -4 still resolves to 32px — no change at
all. To recover a real 48px target you have to pre-pay the trim: add `4px` per
rung.

```css
/* a 48px target at density -4 */
md-checkbox[density="-4"].needs-touch {
  --md-checkbox-touch-target-size: 64px;   /* 64 − 4×4 = 48 */
}
```

See [Density](/behaviour/density/#accessibility).
:::

### Density and direction together

A global `data-density` ancestor and a local `density` prop drive the same
signal — `--md-sys-density-scale` — and the prop lands directly on the host, so
a local rung wins over the inherited one, including inside an RTL subtree.

:::danger[`density="0"` does not opt back out]
There is deliberately **no** `[density="0"]` rule, in the checkbox or in the
token layer: reflected props write `density="0"` onto virtually every element,
so such a rule would pin density-0 values everywhere and break global
inheritance. Absence of a rung means *"inherit whatever the ancestor says"* —
`density="0"` inside `data-density="-2"` still renders at -2. Only `-1` … `-4`
override an ancestor; to escape a dense subtree, put the checkbox outside it.
:::

<ComponentDemo
  html={`<div dir="rtl" data-density="-2" style="display:flex;flex-direction:column;gap:8px;inline-size:100%;">
  <label style="display:inline-flex;align-items:center;gap:8px;"><md-checkbox checked></md-checkbox> بريد إلكتروني</label>
  <label style="display:inline-flex;align-items:center;gap:8px;"><md-checkbox indeterminate></md-checkbox> إشعارات</label>
  <label style="display:inline-flex;align-items:center;gap:8px;"><md-checkbox density="-4" checked></md-checkbox> رسائل قصيرة — density=&quot;-4&quot;</label>
</div>`}
  label="dir=rtl with data-density=-2, and one checkbox overriding to -4"
/>

**Density** — the box and the touch target taper on every rung; the state layer
is clamped by the target (`min(40px, target)`) so it only starts moving at -3.
`--md-checkbox-container-size` and `--md-checkbox-icon-size` are **independent**
properties that merely share the same density-derived default, so overriding one
by hand does not move the other — set both together, as the Theming demo below
does.

**i18n** — translate `supporting-text`, `error-text`, `value-missing-label` and
the visible label text. A hardcoded English `value-missing-label` in a
localized app is the usual oversight; it is a prop precisely so you can feed it
from your dictionary.

## CSS parts

| Part | Element |
|---|---|
| `target` | The hit area — 48px at density 0, 32px at `-4` |
| `state-layer` | Hover / focus / press overlay |
| `container` | The box itself |
| `icon` | The mark — a **Material Symbols glyph**, not an SVG |
| `supporting-text` | The message line under the control |

:::note[`icon` is a font glyph]
It renders `check`, or `remove` when `indeterminate`, at `FILL 1 / wght 600` —
the same face [`md-step`](/components/stepper/#md-step) uses for a completed
step, so the two marks match exactly. Style it with font properties
(`font-size`, `color`, `font-variation-settings`) or `transform`; SVG
properties like `stroke` and `fill` have nothing to act on.
:::
